한눈에

목표는 위임 실험이다. 물리(강체, Jolt)를 AI가 혼자 어디까지 끌고 가는지 본다. 오빠가 확인할 수 있게 테스트, 보이는 샘플, 엔진에 붙는 방식에 대한 짧은 노트를 함께 낸다. 오늘 밤 범위는 설계와 트레이서 불릿이다: Jolt를 트리에 넣고, 고정 틱 위의 물리 월드, 헤드리스 시나리오, 눈으로 보는 플레이그라운드. 물리 월드는 RenderScene 프리미티브에 한 방향으로만 변환을 쓰고, 그 글루는 액터/컴포넌트 라운드가 그대로 옮겨 갈 수 있게 자기 파일에 둔다.

지금까지: 설계(탐색 6, 설계 관점 2 + 비평 1)를 끝내고 작업 넷으로 잘랐다. 작업 1 — Engine/Physics가 Jolt를 완전히 숨기고, 테스트 23개가 결정성(실행 간, 월드 간, 워커 0개 대 3개)까지 확인한다. 작업 2 — 퍼즐 셋(PlateGate, ToppleBridge, SwingDoor)이 헤드리스로 풀리고, 각자의 대조군은 이유를 남기며 실패하고, 여섯 실행의 해시가 체크포인트마다 핀으로 고정됐다. Mac이 이 핀을 그대로 재현하는지가 이 라운드의 열린 질문이다.

이 라운드가 도는 방식

  • 자율. 증분 하나가 끝나면 브랜치 physics에 바로 커밋한다. master, push, amend, rebase, reset은 하지 않는다. 병합은 오빠가 한다.
  • 작업마다 설계 단계. Opus 관점 둘을 읽기 전용 워크플로우로 돌리고, 메인 세션이 합쳐서 작업 파일에 결정을 적은 뒤에 코드를 쓴다.
  • 작업마다 리뷰. 정확성 · 규칙과 스타일 · 테스트 타당성 세 렌즈로 읽고, 발견마다 그것을 반박하려는 검증자 하나를 붙인다. 확인된 것만 다음 작업 전에 고친다.
  • 병행. 같은 시간에 다른 세션이 CrowyEngine-effects에서 GPU 효과를 만든다. 이 라운드의 창은 전부 CROWY_COMMAND_PORT=27600, CROWY_WINDOW_DISPLAY=1로 띄운다.
  • Mac은 멈추지 않는다. Mac에서 확인할 것은 이 라운드 전용 원장 engine-macos-tests-physics.md(PH-n)에 모은다.

라운드 설계에서 정한 것

설계 파일은 engine-design-physics.md(git 제외)다. 탐색 워크플로우(Opus 읽기 6: 렌더 샘플, 코어 수학, 루프·포트·테스트, Jolt, Godot의 Jolt 모듈, worklog 양식과 SmolEngine의 오버랩 이벤트 역사), 설계 워크플로우(관점 둘 "엔진 모양 먼저", "퍼즐과 테스트 먼저" + 비평 하나)를 합쳤다.

  • Jolt는 모듈 안에 숨긴다. Crowy::Physics가 Jolt를 PRIVATE으로 링크한다. Jolt의 PUBLIC 옵션(-mavx2 등과 JPH_* 정의)은 정의가 하나라도 다르면 RegisterTypes가 abort하므로, 정확히 한 묶음의 TU에만 닿아야 한다.
  • 물리는 초가 아니라 틱을 센다. Step() 한 번이 1/60 s 한 틱이고, 물리 쪽에는 dt를 받는 함수가 없다. 한 프레임에 틱을 몇 번 돌릴지는 루프 주인이 정한다.
  • 잰 것이 설계를 바꿨다: 모니터가 120 Hz다. 두 설계 관점 모두 "프레임마다 한 틱"을 제안했지만, 그러면 오빠 화면에서 플레이그라운드가 2배속이 된다. 그래서 플레이그라운드는 정수 나노초 틱 시계(App::FixedStep과 같은 16 666 667 ns)로 실시간으로 돌고, smoke 골든은 리드인 90프레임 동안 틱 0에 멈춘 장면을 찍어 결정적으로 만든다. 움직임은 헤드리스 핀과 포트 확인으로 고정한다.
  • 접촉 이벤트는 이번엔 없다. SmolEngine이 한 달을 쓴 자리(처음부터 겹친 경우, 파괴될 때의 exit, 양방향)이고, Jolt의 리스너는 잡 스레드에서 비결정적 순서로 불리며 잠든 몸체에도 Removed를 낸다. 퍼즐은 겹침 질의(Overlapping)로 읽는다. 이벤트 설계는 설계 파일의 "Deferred"에 액터 라운드 몫으로 적어 두었다.
  • 퍼즐마다 월드 하나. 플레이그라운드가 핀으로 고정된 경로를 그대로 돌게 하려고.
  • Windows와 Mac의 비트 단위 일치는 약속이 아니라 측정이다. Jolt를 CROSS_PLATFORM_DETERMINISTIC으로 빌드했지만 clang-cl은 Jolt의 검증 목록에 없다. 핀은 Windows에서 기록하고, Mac은 맞는지 혹은 어디서 처음 갈라지는지를 적는다. 핀을 Mac에 맞춰 고치지는 않는다.

퍼즐 (physics-puzzles) 완료

BotW 느낌의 퍼즐 셋이 물리 모듈의 공개 API 위의 데이터 표로 들어왔다(Engine/Physics/Sample/Puzzle, 라이브러리 SamplePuzzle). 퍼즐 하나는 몸체(역할 포함), 힌지, 구역, 압력판 규칙, 풀이와 대조군의 입력, 목표(어떤 몸체가 어떤 구역 안에)로 이루어지고, 두 모드는 같은 몸체를 같은 순서로 만든다 — 다른 것은 입력뿐이다. PuzzleSession은 퍼즐 하나를 자기 월드 하나에서 돌린다: 그 틱에 걸린 입력 → 압력판 규칙(직전 틱이 남긴 상태를 읽는다) → Step 한 번 → 목표 래치 → 상태 해시 → 핀과 대조. 월드는 const로만 내보내서 Tick만 월드를 움직이고, 테스트와 플레이그라운드가 같은 길을 돈다.

  • PlateGate. 상자를 밀어 압력판에 올리면 키네마틱 문이 한 틱에 1 cm씩 올라가고, 공이 그 밑으로 굴러 끝벽 앞의 목표에 들어간다. 187틱에 풀린다. 대조군(공만 민다)의 공은 닫힌 문 앞 x = 0.05에서 멈춘다.
  • ToppleBridge. 틈 너머에 선 판을 타격 중심(피벗 모서리에서 0.95 m)에서 밀면 판이 넘어져 틈을 덮고, 공이 그 위를 지나 목표에 든다. 218틱. 대조군의 공은 틈에 빠져 바닥(y 0.15)에서 멈춘다.
  • SwingDoor. 세로축 힌지에 달린 문의 자유단을 밀면 마찰 토크(20 N·m)를 이기고 한계 1.5 rad까지 열리고, 공이 지나간다. 197틱. 공만으로는 문이 0.005 rad 열리고 만다.

핀은 실행 여섯(퍼즐 셋 × 모드 둘)마다 틱 0, 1, 10, 60, 240, 600의 해시와 solvedAt이다. 테스트가 표를 표 그대로의 문법으로 출력하고, Windows에서 한 번 붙여 넣었다. 틱 0은 빌드 자체를, 나머지는 실행을 고정한다.

위임 기록

  • 설계. Opus 관점 둘("견고하고 허용치가 넉넉한 기하", "소비자가 보는 드라이버")을 합쳤다. 퍼즐은 표, 세션은 한 번의 실행, 재시작은 새 세션이라는 모양과 세 퍼즐의 기하는 뒤의 관점(모두 +x로 공이 굴러가서 축이 통일되고 몸체가 적다), 각 퍼즐의 여유 계산과 발자국(월드 AABB) 테스트는 앞의 관점에서 왔다.
  • 실험이 보여 준 것. 세 퍼즐 모두 설계 단계가 계산한 대로 첫 실행에 동작했다. 튜닝이 필요할 거라고 위험 목록 맨 위에 올렸던 ToppleBridge도 그대로 풀렸다(판은 피벗에서 4.7 cm 미끄러진 자리에 눕는다). 계산이 맞힌 수치와 틀린 수치가 함께 있었다: PlateGate 상자의 미끄럼은 1.04 m로 계산했지만 실측은 0.996 m다(선형 감쇠와 틱 단위 적분 때문).
  • 스스로 잡은 것. 첫 실행에서 발자국 테스트가 굴러가는 공을 밖으로 나갔다고 판정했다. 내 테스트 도우미가 구의 경계를 회전한 상자처럼 계산해서 √2배로 부풀렸기 때문이다 — 구의 경계는 회전에 불변으로 고쳤다.
  • 리뷰가 잡은 것. 확인 10건, 반박 14건. 가장 무거운 것: 압력판 규칙의 임계 질량, 동적 몸체만 세는 필터, 내려가는 분기가 어떤 퍼즐에서도 실행되지 않았다(판에 닿는 것은 10 kg 상자뿐이고, 한 번 올라가면 안 내려온다). 그래서 규칙을 "판 위에 아무거나 있으면"으로 바꿔도 테스트도 핀도 안 깨졌다. 레벨 계산을 nextPlateLevel이라는 constexpr 함수로 빼서 따로 시험하게 했고, 핀이 그대로인 것으로 리팩터링이 동작을 바꾸지 않았음을 확인했다. 나머지: 규칙 8(틱 수·몸체 수 단언)을 이번에도 여러 테스트가 빠뜨렸다 — 작업 1의 리뷰가 같은 것을 잡은 직후였는데도. 주석이 실측이 아닌 설계 추정치(1.04 m)를 적고 있었다. 대조군 입력이 풀이의 공 밀기와 같다는 검사가 작용점을 비교하지 않았다. 주석 길이와 과정 언급, 선언 순서, 헤더 인라인 규칙.
  • 반박된 것 중 기억할 것. "틱 0 핀이 빌드를 고정한다"는 말이 과하다는 지적(Jolt의 SaveState는 모양·질량·재질·힌지 한계를 쓰지 않는다)은 반박됐지만 사실 자체는 맞다 — 틱 0 핀이 잡는 것은 위치·회전·속도·수면 상태다. 대조군 테스트가 공이 장애물까지 갔는지를 확인하지 않는다는 지적도 반박됐다(추적 출력에서 공은 문 바로 앞에서 멈춘다).
  • 막힌 곳. 없다.
  • 남겨 둔 것. 퍼즐을 파일(JSON)로 읽는 것 — 지금은 C++ 리터럴이다. 규칙 4(Jolt에 들어가는 것은 리터럴과 사칙연산)를 지키려고 회전은 모두 단위 쿼터니언이다. 세 번째 이상의 메커니즘(도르래, 미닫이, 부력)과 접촉 이벤트로 도는 규칙.
  • 직접 다시 설계할 것 같은 곳. 퍼즐을 C++ 표로 쓴 것. 오빠가 퍼즐을 직접 만든다면 데이터 파일과 에디터 쪽이 먼저일 것 같다. 그리고 핀이 Mac에서 어긋나면 ctest -L unit이 Mac에서 늘 빨갛게 남는다 — 그게 "발견"이라는 규칙은 내가 정했지만, 플랫폼별 핀 표나 결정성을 포기하는 쪽을 오빠가 고를 수도 있다.

물리 월드 (physics-world) 완료

Jolt v5.6.0이 FetchContent로 들어왔고, 새 모듈 Engine/Physics가 그것을 완전히 감싼다. 공개 헤더 셋(PhysicsTypes, PhysicsRuntime, PhysicsWorld)에는 Jolt 타입이 하나도 없다. PhysicsRuntime은 Jolt의 프로세스 전역(할당자, Trace와 Assert 훅, 팩토리와 타입 등록), 잡 시스템, 임시 할당자를 가진다 — 프로세스에 하나, 모든 월드보다 오래 산다. PhysicsWorld는 그것을 빌려서 박스와 구 몸체(정적·키네마틱·동적), 월드에 거는 힌지(한계와 마찰 토크), 중심이나 한 점에 거는 임펄스, 키네마틱 목표, 겹침 질의, 상태 해시를 1/60 s 고정 틱 위에서 돌린다.

핸들에는 만든 월드의 태그가 들어 있어서, 다른 월드의 핸들은 거부된다(플레이그라운드는 월드 셋을 동시에 돈다). 키네마틱 목표는 들고 있다가 매 Step마다 다시 낸다 — Jolt의 MoveKinematic이 설정한 속도는 그대로 남기 때문이다. 상태 해시는 틱 수와 PhysicsSystem::SaveState가 쓰는 모든 바이트(몸체, 속도, 수면 상태, 워밍 람다를 포함한 접촉 캐시, 구속)에 대한 FNV-1a로, Jolt 스스로 결정성을 검사할 때 비교하는 그 상태다.

위임 기록

  • 설계. 라운드 설계는 위의 "라운드 설계에서 정한 것". 작업 설계는 Opus 관점 둘("Jolt에 충실한 최소 래퍼", "소비자 — 퍼즐, 글루, 액터 라운드")을 합쳤다. 상태 해시를 Jolt의 SaveState 위에 세운 것은 앞의 관점, 핸들의 월드 태그와 ShapeOf/MotionOf는 뒤의 관점에서 왔다.
  • 설계가 바뀐 곳. 작업 파일이 적은 휴식 높이 [0.49, 0.51]이 틀렸다. 두 관점이 각자 Jolt의 적분을 float로 다시 돌려 0.486을 냈고, 테스트는 [0.479, 0.501]로 갔다. 설계 파일의 "박스의 반 크기는 볼록 반경보다 커야 한다"도 5.6에서는 맞지 않는다(반경을 가장 작은 반 크기로 자른다). "다른 월드의 핸들은 못 잡는다"던 작업 파일의 한계는 월드 태그로 없어졌다.
  • 스스로 잡은 것. Jolt의 CMake를 빌드 전에 읽어서 함정 넷을 먼저 피했다: clang-cl은 MSVC로 잡혀 정적 런타임(/MTd)이 기본이 되고 트리는 /MDd라 링크가 깨진다, clang-cl의 /Wall은 -Weverything이라 /WX와 만나면 새 clang에서 깨진다, v5.6의 GPU 헤어 시뮬레이션이 DX12/Vulkan/Metal 셰이더 툴체인을 끌고 온다, clang-cl 경로에서는 Jolt가 -ffp-contract=off를 넣지 않는다. 그래서 첫 빌드가 경고 0으로 통과했다. 레드 런: 키네마틱 목표 재발행을 빼면 KinematicReachesAndHolds가 속도 60 m/s가 남은 채로 실패한다.
  • 리뷰가 잡은 것. 확인 15건, 반박 11건. 겹치는 것을 합치면 열한 가지다. 무거운 것부터: 테스트 14개 중 12개가 틱 수와 몸체 수를 단언하지 않았다(라운드 규칙 8 위반 — 몸체가 없는 두 월드도 "해시가 같다"를 통과한다). 해시가 틱에 의존한다는 것을 보이는 테스트가 없었다. 마찰·반발·각 감쇠·힌지 마찰 토크는 기본값이 Jolt의 기본값과 같아서, 그 값을 Jolt에 넘기는 줄을 지워도 모든 테스트가 통과했을 것이다. 쿼터니언 변환은 y와 w만 지나갔다. 다른 월드의 힌지를 거부하는 검사는 그 월드에 힌지가 아예 없어서 공허했다. 그리고 내가 쓴 주석 "결정성 빌드는 속도의 약 8 %"가 Jolt 문서의 "약 8 % 느리다"를 열두 배 느리다로 바꿔 적고 있었다. 나머지는 80열, 쓰이지 않는 const 오버로드, 긴 타입 별칭, 생성자에서 멤버 이름 매개변수를 쓴 것.
  • 반박된 것 중 기억할 것. Release에서 무효 핸들을 역참조한다는 지적은 맞지만 범위 밖이라는 판단(Debug에서는 assert, PackedTable::GetRef와 같은 계약)이 이겼다. 키네마틱 목표가 해시에 안 들어간다는 지적은 "입력이지 상태가 아니다"로 반박됐다.
  • 막힌 곳. 없다.
  • 남겨 둔 것. 몸체 제거, 텔레포트, 레이어·마스크, 레이캐스트, 캡슐과 메시, CCD, 디버그 렌더러, 접촉 이벤트. 하나씩 새 멤버나 variant 대안으로 들어오고 시그니처는 바뀌지 않는다. Mac에서 RTTI가 섞이는 링크 위험(Jolt는 /GR-, 엔진은 RTTI)은 원장 PH-1에 적었다 — 모듈은 Jolt 클래스를 상속하지 않는다.
  • 직접 다시 설계할 것 같은 곳. 월드 태그를 GenericHandle의 generation 상위 32비트에 접어 넣은 것. 동작은 하지만 핸들 타입이 모르는 약속이라, 오빠라면 핸들에 소유자 필드를 두거나 월드를 하나로 합쳤을 것 같다. StateHash가 부를 때마다 문자열 스트림으로 상태 전체를 직렬화하는 것도 — 틱마다 부르면 무겁다(지금은 테스트와 체크포인트만 부른다).
