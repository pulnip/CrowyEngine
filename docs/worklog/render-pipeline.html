왜 이 라운드였나

앞 라운드(렌더 반복 도구 상자, 2026-09-24~26)가 계측, 셰이더 리로드, 프로토타이핑 맵 Playground와 디버그 뷰, 이미지 비교를 만들었다. 그 도구가 없으면 파이프라인 설계는 실험마다 빌드하고 판정마다 눈대중이 된다는 것이 그때의 논거였고, 표준 렌더링 파이프라인은 그 다음 라운드로 미뤄졌다.

그 라운드의 Windows 패스가 닫힌 2026-09-27, 직접 요구를 하나 더했다: 레퍼런스 스타일(A Short Hike의 셀 룩, 스타일라이즈드 메탈, 세피아 2단 하드 섀도, 종이 위 하프톤, 라인아트 수채)과 PBR을 모두 그릴 수 있어야 하고, 손대지 않은 기본값은 "모델을 놓으면 그려지는" 진짜 파이프라인이되 교체가 싸야 한다. 이 요구가 설계 질문 전부(material/pass 분리, BuildFrame의 형태, args 버퍼 공유, light row의 내용)를 재편했고, 그래서 작업을 자르기 전에 설계를 한 번에 고정하는 단계를 먼저 두었다 — 이 라운드가 처음이다.

처음 추정은 작업 두셋이었고, 설계 뒤에는 여섯 작업 약 16증분으로 올라갔으며, 실제로는 21증분이 됐다.

결정과 규칙

소유자 결정 (2026-09-27)

Shape C

표준 파이프라인은 스타일 중립, 셰이딩 모델은 머티리얼별 선택. 기본 PBR(glTF metallic-roughness, Playground.slang의 GGX), Toon을 첫 대안으로 이번 라운드에. 기각 A(PBR 표준 + NPR 별도 파이프라인): 직접의 관심사가 증명용 부록이 되고 셰이더 실험마다 파이프라인 전체가 필요. 기각 B(toon 표준 + PBR 두 번째): metallic × roughness 차트가 의미를 잃음.

Seam은 Slang 모듈 링킹

link-time type. 새 모델은 파일 하나, 패스 셰이더는 그대로. 기각: 패스 셰이더 안의 enum switch(모델마다 Engine/Render 편집), 머티리얼이 fragment shader 전체를 지명하는 현행 방식(라이트 루프·섀도·톤맵이 셰이더마다 복사됨).

Forward 전용

depth prepass + forward 셰이딩, G-buffer 없음. deferred가 필요해지면 자체 레이아웃의 별도 파이프라인. 직접 지목한 함정: 기계적으로 중립을 유지한 G-buffer가 두 스타일의 대역폭을 모두 지불한다.

교체를 이번 라운드에서 증명

다른 패스 리스트의 두 번째 파이프라인을 Engine/Render 바깥에서 조립해 자체 골든으로 Playground를 렌더. 스타일은 무엇이든 무방.

시작 시점의 결정

  • Windows 우선. D3D12(디버그 레이어, GBV)에서 구현·검증하고 Metal 절반은 블라인드로 쓰며, 증분마다 macOS에서 확인할 항목을 적어 두고 나중에 macOS에서 테스트한다. Metal만 답할 수 있는 세 질문(Depth32Float를 texture2d<float>로 읽는가, link-time type이 whole-program 경로에서 링크되는가, position invariance)을 위해 체크포인트 둘을 일찍 둔다 — 깊이 읽기 작업 뒤, seam 작업의 두 번째 증분 뒤. 폴백은 desc나 셰이더 편집 수준으로 유지.
  • 순서는 라이트가 seam보다 먼저: 깊이 읽기 → 패스 분리 → 프레임 파이프라인 → 라이트·섀도 → 씬 컬러·seam → toon 증명. 어디에도 static const 태양을 임시로 두지 않음.
  • 줄여야 할 때 자를 순서: point/spot 행 → 중간 결과 캡처 → prepass 벤치 → Posterize. 실제로는 하나도 자르지 않았다.
  • 시작하며 바로잡은 넷: prepass는 처음부터 별도의 depth-only RHI 패스(색 패스 안에서 write mask 0은 RHI 규칙과 Metal의 포맷 매칭을 깸); Compose는 포맷으로 fragment stage를 정함; LightSample은 Shading.slang에(임포트된 모듈은 임포터의 include를 못 봄); 섀도맵은 클래스가 아닌 frame target.

네 가지 규칙

"중립"은 기계적일 때 함정이다. 모든 작업이 자기 설계를 이 넷에 비춰 판단했다.

1. Forward, G-buffer 없음. 중립성은 인터페이스(Surface, LightSample, 패스 종류)에 두고 버퍼 레이아웃에 두지 않는다. 닫는 함정: G-buffer 비트 예산 때문에 셰이딩 모델 집합이 16개로 닫히는 UE의 형태.
2. 셰이딩 훅은 Godot light() 형태, UE의 switch가 아님. 엔진이 라이트 루프와 섀도 샘플링을 소유하고 모듈은 라이트 하나씩만 본다. NPR 파라미터는 엔진이 해석하지 않는 레인 둘. 닫는 함정: 모델마다의 엔진 편집.
3. 패스는 opt-in, 최대 집합이 아님. 리스트에 없는 패스는 타깃·draw list·파이프라인 비용이 0. 닫는 함정: 두 스타일 몫을 늘 지불하는 "PBR도 NPR도 아닌 프레임".
4. 중립성은 가정이 아닌 검증. 두 번째 파이프라인이 합격 테스트. 조립에 Engine/Render 수정이 필요하면 그것이 라운드의 발견. 결과: 두 백엔드 모두 발견 없음.

설계 14절

2026-09-27에 고정한 설계의 14절을 각각 두세 문장으로. 이름은 모두 제안이었고 각 작업의 설계 단계에서 확정됐다. "pipeline"이 이미 파이프라인 상태를 뜻해서 프레임 쪽은 FramePipeline이라 불렀다.

1. 패스는 값, 파이프라인은 그 리스트

PassDesc(mesh / fullscreen의 std::variant)와 FramePipelineDesc. 데이터인 이유: walker가 기록 전에 모든 사용을 봐야 release와 acquire를 같은 값으로 짝지을 수 있고, 값이면 디바이스 없이 테스트·diff가 된다. edge는 타깃의 연속 사용 쌍마다 하나(read → read 포함 — Metal에서 두 번째 release가 첫 번째를 stale로 만듦), 첫 사용은 cross-submission acquire.

2. walker와 프레임 순서

FramePipeline(Resize, Prepare, Record, Overlay, Stats)이 desc, 타깃 텍스처, 패스별 DrawList, edge, fullscreen 파이프라인, 패스별 통계를 소유. RenderApp의 봉인된 프레임 순서는 유지되고 선택은 가상 함수 하나 DescribePipeline. Metal이 패스마다 바인딩을 새로 시작하므로 push와 CB는 패스마다 재설정.

3. Draw list, 뷰당 컬링 1회, 정렬 키

BuildFrame을 Frame(BeginFrame) / View(Visible) / Pass(DrawList::Build) 세 층으로. 각 리스트가 자기 transient slice를 소유해 "args 버퍼 공유" 질문이 닫힘. 정렬 키는 u64 하나: 불투명 run:16 | depth:32 | identity:16, 반투명 ~depth:32 | identity:32.

4. material/pass 분리

머티리얼은 VS, 기본 FS, topology, cull, blend, domain, shadingModule. 패스는 포맷, depth 상태, fragment override, PassDepthBias, linksShading, 디버그 override. 유리의 depthWrite = false는 domain = Translucent로. 위치 불변성은 PrepassEqualSpike로 측정, 폴백 사다리 LessEqual → 바이어스 → [[invariant]] → 백엔드별 prepass off.

5. 씬 데이터로서의 라이트

LightKind {Directional, Point, Spot}, LightSnapshot, EnvironmentSnapshot; GPU 행 LightData 128 B; ScenePush 32 → 56 B(lights, lightBase, lightCount, shadowMap); ambient 쌍은 ViewData. 의도적 부재: specular/diffuse scale, IES, mask, bake, volumetrics.

6. 섀도맵

직교 뷰를 매 프레임 Visible 바운드 합집합에 fit(카메라 독립, 흔들림 없음). 고정 2048² D32 frame target ShadowMap, view 1의 depth-only 패스. 수신측 바이어스(L 방향 상수 + 1 − N·L 노멀 오프셋, Godot omni/spot 형태). Load + 비교 1회로 정확히 0 또는 1; 라이트·섀도 작업의 다섯째 증분이 선택적 2×2 PCF를 기본 off로 추가.

7. 씬 컬러, post 리스트, UI

오프스크린 RGBA16F, 클리어 색이 씬 radiance. Tonemap.slang = 기존 toDisplay, 선형 → display 경계. 반투명은 톤맵 전 선형 HDR에서 블렌드(골든 재기록 1회). appendPostChain이 항목 리스트를 ping-pong 패스로, UI는 마지막 패스에. 디스플레이용 샘플 넷은 {Present}로 바이트 동일 유지.

8. 셰이딩 seam

extern struct MaterialShading : IShadingModel / export struct … = ToonShading;. RHIShader가 모듈을 composite에 로드, linkedModules가 파이프라인 키. Shading·Lighting·ForwardShading.slang과 모듈 PBR·Toon·Unlit; 기본값 UnlinkedShading(마젠타)이 depth-only의 E45001을 막음. MaterialData 80 B, 레인 custom0/1.

9. 디버그 뷰

5개 모드는 ForwardShading.slang을 거쳐 남고 wireframe·overdraw는 패스 override. 데이터 뷰(normals, depth, overdraw, shadow)는 post 리스트를 {Present}로 바꾸고 검정으로 클리어. 새 모드 Shadow.

10. 중간 결과 캡처

Copy(texture → buffer)와 GetReadbackRowPitch. capture_frame {target}: 타깃이 없으면 기존 스왑체인 경로, 있으면 TargetCaptureQueue. 프레임 끝 blit 패스 하나가 모든 캡처를 운반, 다운로드는 GetCompletedFrame() 폴링(held 루프는 submit하지 않음). smoke_run은 백버퍼만 계속 게이트.

11. 표준 파이프라인

makeStandardPipeline(StandardPipelineConfig): Shadow → DepthPrepass → Opaque(Equal) → Translucent → {Tonemap}. depthPrepass = false면 prepass가 빠지고 Opaque가 Less + write; debug.depthPrepass로 런타임 전환(재빌드). 라이트 없는 샘플은 shadowMapSize = 0으로 opt-out.

12. 증명: ToonPlayground

플래그가 아닌 두 번째 실행 파일(smoke_run이 골든을 실행 파일 이름으로 짓고 cmake가 실행 파일마다 smoke 테스트 등록). PlaygroundScene 위의 두 main. shadow → normals prepass → opaque(Toon, 패널은 Unlit) → outline → translucent → {Tonemap, Posterize}. 합격은 명령 하나: 엔진 디렉터리의 git status가 비어 있을 것.

13. RHI 작업

작고 스타일 무관, 각각 검사가 있음: (a) 색 첨부 0개 허용, (b) std::optional fragment stage(19개 사이트), (c) typed optimized clear value, (d) 깊이 읽기 규칙, (e) linkedModules, (f) texture → buffer 복사, (g) CastShadow 기본값. 스파이크 둘: ShadowSampleSpike, PrepassEqualSpike.

14. 디바이스 없는 테스트

FakeCommandList가 두 백엔드의 배리어 짝짓기 규칙을 모방해 누락된 Metal edge를 어느 머신에서나 테스트 실패로 만든다. FakeDevice는 CPU AllocateTransient와 FakeTexture. ComposedPipelineTest는 공개 헤더만으로 toon 모양 desc를 지어 스타일 이전에 규칙 4를 검사.

카메라 핏과 캐스케이드 — 다음 단계로 측정됨 (2026-09-29)

Playground 방은 27.87 m 정사각, 2048² 맵 하나에 텍셀 1.36 cm, 1.5 m 거리에서 5–6픽셀. 태양이 스치는 수신면에서 텍셀이 1/(N·L)로 늘어남 — 니치 뒤판 2.3×, x 방향 벽 4×. 맵 격자가 월드 격자에서 30° 틀어져 월드 축 직선 엣지가 규칙적인 계단이 되고, 2×2 PCF는 계단을 텍셀 하나 폭의 띠로 부드럽게 할 뿐 없애지 못함(샘플을 더하지 않음). 엣지를 주름에서 옮겨도 변화 없음 → 원인은 지오메트리가 아닌 샘플링.

형태: Godot 방향광 기본 4 분할. 뷰 프러스텀을 거리로 나눠 분할마다 직교 fit — bounding sphere(카메라 회전 시 fit이 숨쉬지 않게), 정수 텍셀 스냅(이동 시 엣지가 기지 않게), pancaking. 근거리 분할 약 3 m면 텍셀 약 0.15 cm, 9배 정밀. 구조 변화: ShadowFit이 카메라 프러스텀을 받아 분할별 fit; LightData의 shadowIndex가 섀도 블록(두 번째 structured buffer, spot 그림자가 재사용)을 가리킴; atlas면 패스별 viewport, texture array면 슬라이스별 부착 — 어느 쪽을 RHI가 받을지가 두 백엔드의 첫 질문; N 섀도 뷰가 FramePipeline을 특수 케이스 없이 통과하는지 시험. 크기 작업 약 3개. 임시방편은 4096² 또는 8192² 맵(64 또는 256 MiB).

크기를 센 후보

  • modern Slang module 이전: Shading.slang 단독 19 public; 전체 헤더 12개 약 200 public, 1–2일, macOS 테스트. entry point·파라미터 선언 헤더가 장벽.
  • 룩 seam 재방문: 머티리얼별 lit/shade 색 쌍, 색 있는 bounce, 탈채도하지 않는 톤맵 — 레인 둘에 두 번째 색 쌍이 들어가지 않음.

기록만 하고 고치지 않은 것

  • 반투명은 바운드 중심 정렬; 패스 params는 실행당 고정; 메시의 파이프라인 몫 비어 있음.
  • Metal은 independentBlendEnable 없이 모든 attachment를 블렌드; 셰이더 프로그램 캐시 없음; Metal에서 패스 밖 이벤트 스코프는 라벨 없음.
  • PackedTable::Clear가 이전 핸들을 되살림; smoke_run이 캡처 없이 exit 0; ImageCompareCheckSmoke 플레이크.
  • D16/D24S8/D32S8 깊이 읽기 행 미실행; i32 → float depth bias의 Metal 의미 미검증.

회고

  • 설계를 먼저 고정한 것이 맞았다. 한 후보가 설계 질문 묶음일 때 설계를 한 번에 고정하지 않으면 작업 셋이 같은 결정을 다시 끌어낸다. 이 방식을 앞으로의 라운드에도 쓴다(2026-10-03 직접 결정).
  • Windows-first가 통했다. 두 체크포인트가 폴백 없이 통과했고, macOS가 찾은 둘(redundant-state 경고, ulp 하나)은 모두 Windows가 볼 수 없는 종류였다. FakeCommandList가 Metal의 짝짓기 규칙을 모방한 것이 디바이스 없이 edge 누락을 잡는 첫 방어선으로 작동했다(red 2).
  • 기록 규율의 구멍, 다음 라운드가 고칠 것:
    • 커밋한 뒤에도 "아직 커밋 안 됨"이 네 작업의 기록에 남았다 — 커밋한 세션이 해시를 써 넣는다.
    • 한 작업은 증분별 실측(불변성 수치, 스파이크 on/off, 벤치)을 기록에 옮기지 않았다 — 실측은 macOS 테스트 쪽에만 남았다.
    • macOS 확인 항목의 번호 체계를 작업마다 따로 매겨 충돌했고, 뒤 작업이 바꾼 수치(renderPasses 3·4 → 4·5)가 앞 항목에 그대로 남았다.
    • 같은 날 두 작업이 clang-format에 대해 반대로 적었다(바뀐 파일마다 돌림, 승인됨 / 묻기 전엔 금지).
