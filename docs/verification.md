# 검증 설계

이 엔진은 AI 페어 프로그래밍 방식으로 만들었다.
다만, 검토 속도보다 구현 속도가 월등히 빠르므로, AI가 만든 코드를 **기계적으로 그리고 스스로 검증**할 수 있는 환경이 필요했다.
이 문서는 그 방법을 설명한다.
- 테스트 종류
- golden
- 실행 중인 앱을 밖에서 조작하고 읽는 명령 포트
- 그 밑에 깔린 리플렉션.

세부 규칙 원문은 [testing.md](testing.md)에 있다.

## 테스트 종류

ctest 라벨로 그 테스트에 필요한 것과 언제 실행해야 하는지 정한다.

| 라벨 | 필요한 것 | 지키는 것 |
|---|---|---|
| `unit` | CPU만 | 함수·클래스 계약, RHI 호출(fake 위에서), 참조 모델, 시드 고정 fuzz |
| `gpu` | 디바이스, 창 없음 | `*Check`: GPU 결과를 CPU 참조 구현과 비교. 틀리면 0이 아닌 값으로 종료 |
| `render` | 창 | `*Spike`: 백엔드 동작 하나를 frame 60 golden 이미지로 고정 |
| `app` | 창 + 콘텐츠 | 호스트가 스스로 시작하고, 프레임을 돌고, 종료까지 assert나 debug layer 에러 없이 끝나는지 |
| `scenario` | CPU, 긴 시뮬레이션 | 물리 퍼즐이 풀리는지, tick별 상태 해시가 고정값 그대로인지 |
| `content` | 외부 repo `../Backlot` | 외부 씬이 고정 커밋 기준으로 import되는지. 없으면 skip |

코드가 수정된 범위에 따라 돌려야 할 라벨이 정해진다.
- RHI를 건드리면 `gpu|render`,
- 창 경로를 건드리면 `app`,
- 로직이 아직 바뀌는 중일 때는 `unit`만.

테스트가 너무 많이 생기거나, 너무 자주 실행하는 걸 막기 위해 몇 가지 원칙을 세웠다.

- **테스트는 기능 마다가 아니라 결함 종류마다**
  "새 코드라서", "커버리지 때문에"는 이유가 안 된다.
  잡으려는 잘못된 동작과 그게 왜 생길 수 있는지를 먼저 설명해야 한다.
- **그 결함을 확인할 수 있는 가장 싼 종류를 고른다.**
  `static_assert` / assert → `unit` → `gpu` → `render` → `app` 순서다.
- **고정값은 코드를 돌려서 얻은 값이어야 한다.**
  해시, tick 수, 픽셀 수는 손으로 타이핑하지 않고 검사하는 도구로 기록한다.
- 자기 setup을 그대로 다시 확인하는 테스트는 아무것도 증명하지 않으므로 지운다.

## golden

어떤 결함은 렌더링 결과물이 틀어지는 형태로 나타나는데, 사람이 느끼지 못할 정도로 작을 수 있다.

instance id의 기준값, 깊이 prepass와 Equal 테스트 사이의 위치 불변성, 그림자 비교 샘플링은 D3D12와 Metal에서 다를 수 있고,
래스터라이저와 깊이 테스트, 샘플러 등을 모두 거친 결과라서 CPU 참조 구현으로 다시 만들기도 어렵다.

그래서 `*Spike`는 그 동작 하나만 그리는 작은 실험이다.
사람이 결과를 보고 맞다고 판정하면 그 그림을 golden으로 저장하고,
이후에는 기계가 매번 같은 그림이 나오는지 비교해서 그 판정을 유지한다.

참고로, 캡처할 때는 고정 스텝을 사용하므로, 주사율이나 프레임 시간과 상관없이 같은 그림이 나온다.
비교 기준과 새 그림을 받아들이는 방법은 [testing.md](testing.md)에 있다.

## 명령 포트: 실행 중인 앱을 AI가 스스로 확인하는 방법

테스트는 미리 정해둔 결함만을 확인한다.
테스트를 추가하지 않는 대부분의 변경, 실제 앱에서의 동작에 대해서도 검증할 방법이 필요하다.
그런데, AI는 창을 직접 보거나 패널을 누를 수 없으므로 별도 방법이 필요하다.

Debug 빌드에서 `FrameHost` 위에 선 렌더러 샘플은 로컬 HTTP 포트로 명령을 받는데([CommandPort.hpp](../Engine/Remote/Public/CommandPort.hpp)), 명령 종류는 아래와 같다.

- **조작**: 리플렉션으로 등록된 값을 읽고 쓴다. 사람이 패널에서 바꾸는 값과 같은 경로다.
- **관찰**: 프레임을 캡처하고 프레임 통계를 읽는다.
- **진행 제어**: 앱을 멈추고, N프레임만 돌리고, 특정 프레임까지 기다린다.
  앱이 계속 돌면 읽은 값이 어느 시점의 것인지 매번 달라지므로, 같은 결과를 얻으려면 이 제어가 필요하다.
- **입력**: `--port-input`으로 띄운 앱에 키보드·마우스 입력을 넣고(`push_input`), 앱이 본 입력을 읽는다(`read_input`).

전체 verb와 각 verb가 받는 인자는 포트의 `GET /`가 보여 준다.

```bash
curl -X POST http://127.0.0.1:27500/rpc \
  -d '{"cmd":"set_property","args":{"target":"debug","path":"wireframe","value":true}}'
```

이를 통해, AI가 자신의 기억에 의존해서 고쳤다고 말하지 않고, 앱을 띄우고 실제 동작을 확인하며 고칠 수 있게 만든다.
사람 또한 동일한 명령으로 같은 결과를 확인할 수 있으므로, 재현 가능한 증거로도 쓸 수 있다.

## 리플렉션: AI가 확인한 결과를 믿을 수 있는 이유

명령 포트는 특정 타입을 모르고, 등록된 리플렉션으로 값을 읽고 쓴다.
ImGui 인스펙터도 리플렉션을 사용하므로, 동일한 값 수정 경로를 거친다.

```cpp
CROWY_STRUCT(RenderDebug)
    .SetProperty("mode", &RenderDebug::mode)
    .SetProperty("wireframe", &RenderDebug::wireframe)
    .SetProperty("shadowFilter", &RenderDebug::shadowFilter)
    // ...
CROWY_STRUCT_END(RenderDebug)
```

- **사람과 같은 경로** 테스트 전용 경로가 따로 없으므로,
  AI가 포트로 확인한 동작은 사람이 패널에서 겪을 동작과 같다.
  에디터 조작도 결국 프로퍼티 쓰기라서 스크립트로 그대로 재현된다
  ([Tools/stage_task.ps1](../Tools/stage_task.ps1)).
- **확인할 수단이 기능마다 따로 필요하지 않다.** 새 값을 등록하면 그 값은 바로 포트에서 읽고 쓸 수 있다.
- **잘못된 경로는 실패한다.** 없는 경로나 맞지 않는 타입을 쓰면 포트는 에러로 응답한다.
  스크립트가 아무것도 바꾸지 않은 채 통과하는 일이 없다.
